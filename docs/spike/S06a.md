# S06a: Refund and void

Run on 2026-11-12 against the PayPal sandbox with `scripts/spike/02-refund-void.ts` and the S04 client, in session N3. Raw, redacted exchanges are in the gitignored `.spike-logs/S06a/`.

## Results

- **Q6 answered: no, a refund does not restore capacity.** The same $30 capture was refused before and after a $40 refund, with the same error, while a $5 capture still fit. This matches arch 7.3: refunded money is never offered as spendable. No design change is needed.
- **Q4 (void part) answered: yes.** The uncaptured remainder of a partly captured authorization can be voided. The authorization went from `PARTIALLY_CAPTURED` to `VOIDED`, and a later capture on it was refused. The reauthorized-hold part of Q4 waits for S06b (blocked until 2026-11-13T07:46Z).
- **Q5 (refund and void):** replaying a refund or a void with the same `PayPal-Request-Id` returns the original result and moves no money. A second refund of the same capture under a new request ID is refused (`CAPTURE_FULLY_REFUNDED`), so a refund can't happen twice either way.
- **Refunds still work after a void.** A capture on a voided authorization can still be refunded, so refunds on closed pools (arch 5.4) work.
- **PayPal allows captures up to 115% of the order amount by default.** Kitty never uses this, because the database constraint `pools_never_overspent` keeps captures within `authorized_cents`.
- **One defect found and fixed:** the client classified PayPal's refusal of an over-limit capture (`MAX_CAPTURE_AMOUNT_EXCEEDED`) as `unknown`. It is now `failed`, with a test. See below.

Every refused call left the order unchanged on the next read. At the end, the order showed 4 captures ($95.00) and 2 refunds ($60.00): captures #1 and #3 `REFUNDED`, #2 and the $5 probe `COMPLETED`.

PayPal's text for the over-limit refusal says the default overage limit is 115%, "which allows the sum of all captures to be up to 115% of the order amount". The probes were sized so that limit couldn't fake a result: $90 + $30 = $120 is above $115, while $50 + $30 = $80 would have fit if the refund had restored capacity.

## Replays (Q5)

- **Refund:** the same request ID returned the original refund with HTTP 200 instead of 201. No second refund was made, and the refunded total stayed $40.
- **Void:** the same request ID returned `VOIDED` with HTTP 200.
- **New request ID on a fully refunded capture:** refused with `CAPTURE_FULLY_REFUNDED`, so the money is safe even without the header.
- S05 already showed capture replays return the original capture (and echo the replayed amount).

## What this means for Kitty

- **The ledger rule stands.** `refundPurchase` already keeps the member's limit used and offers no refunded money as spendable (arch 7.3, S43). No ADR is needed.
- **Closing works as built.** `closePool` voids the remainder through `releaseHold`, and the rail's `kitty-void-{authorization.id}` request ID is replay-safe.
- **Refunds after close work.** S43's "refund on a closed pool" case has a real-sandbox basis.
- **Classification fix.** `MAX_CAPTURE_AMOUNT_EXCEEDED` joins `DEFINITE_FAILURE_ISSUES` in `src/adapters/payments/paypal-client.ts`, because the order read proved no capture was made. Before this, a refused capture would have stayed `capture_unknown` with its funds reserved. `AUTHORIZATION_VOIDED` and `CAPTURE_FULLY_REFUNDED` stay `unknown`, because a replay of a request that already worked can also produce them.
