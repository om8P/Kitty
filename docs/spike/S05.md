# S05: Authorize and partial captures

Run on 2026-11-10 against the PayPal sandbox with `scripts/spike/01-capture.ts` and the S04 client. Raw, redacted exchanges are in the gitignored `.spike-logs/S05/`.

## Results

- **Q1 answered: yes.** A default sandbox business account takes multiple partial captures on one authorization with no PayPal approval step. Every capture used `final_capture: false`.
- **Q2: at least 30.** 30 captures on one $150 authorization all succeeded, and no cap was hit. This is a lower bound, not PayPal's limit.
- **Q5 (capture, immediate and after 1 hour):** replaying a capture with the same `PayPal-Request-Id` returns the original capture and moves no money. **But the replay response echoes the new request's amount**, so it cannot be trusted for amounts. See below.
- **New blocker found and fixed:** the seller and buyer must be able to transact in USD. Non-US sandbox accounts block approval.

## First attempt: currency block

The first order (`96R87841NC019613E`, under the sandbox accounts from S02) could not be approved. After the buyer signed in, PayPal's checkout showed "This seller doesn't accept payments in your currency" and the order stayed `PAYER_ACTION_REQUIRED`. The API gave no error: creating the order succeeded, and the problem only appeared in the buyer's browser.

The fix was a new US business account, a new sandbox app linked to it, and a new US personal buyer. The order then approved first time.

For Kitty: pool approval can fail on PayPal's page with no API signal, so the pool simply stays `awaiting_payer`. The return and cancel routes (S24) need a timeout path to `abandoned`, which arch 5.1 already has. The README (S52) must tell judges to use US sandbox accounts.

## Partial captures (Q1, Q2)

| Captures | Amounts | Result |
|---|---|---|
| #1 to #3 | $20, $15, $10 | `COMPLETED`, HTTP 201 |
| #4 to #30 | $2 each | `COMPLETED`, HTTP 201 |
| Total | $99.00 of $150.00 | Authorization `PARTIALLY_CAPTURED` |

- Each capture took about 1 to 2 seconds.
- **The order status becomes `COMPLETED` after the first capture**, while the authorization stays `PARTIALLY_CAPTURED` and keeps taking captures. Pool state must be read from the authorization, never from the order status (S22 `getPoolPaymentState`).
- `GET /v2/checkout/orders/{id}` lists every capture under `purchase_units[0].payments.captures`, so captures can be totalled from one read call (also needed for S07 and S45).
- No 422 issue codes were seen, so `paypal-client.ts` needs no changes from this step.

## Capture replay (Q5)

Capture #1 (`60S63968MU144903F`, $20.00, request ID `s05-capture-42D18536AN884403G-1`) was replayed with the same request ID.

| When | Body sent | HTTP | Returned capture | Amount in response | Money moved |
|---|---|---|---|---|---|
| Original | $20.00 | 201 | `60S63968MU144903F` | $20.00 | yes |
| +35 s | same, $20.00 | **200** | same ID, `COMPLETED`, original timestamps | $20.00 | no |
| +36 s | **different, $1.00** | **200** | same ID, `COMPLETED`, original timestamps | **$1.00** | no |
| +1 h 1 min (08:48Z) | same, $20.00 | **200** | same ID, `COMPLETED` | $20.00 | no (still 30 captures, $99.00) |
| Next day | same | optional | | | |

- **A replay is safe:** no second capture, and the order still showed 10 captures and $59.00 afterwards.
- **A replay answers 200 where the original answered 201.** That difference shows a response is a replay.
- **PayPal does not check the replayed body.** A different amount with the same request ID still returns the original capture, but the response's `amount` is the **new request's** value. `GET /v2/payments/captures/60S63968MU144903F` afterwards showed the true stored amount, $20.00.

For arch 7.2 and S31: the existing design already fixes the request ID and amount for the life of a purchase, so a replay always resends the same body. In addition, the ledger must settle a capture using **the purchase's own amount plus the returned capture ID**, never the amount in a capture response. If an amount ever disagrees, read the capture with `getCapture`. This adds to arch 7.2 rather than changing a decision, so the arch edit is left for S08.
