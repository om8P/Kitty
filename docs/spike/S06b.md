## Results so far

- **Q3, when: only from day 4 to day 29.** Reauthorizing inside the 3-day honor period is refused with HTTP 422 `UNPROCESSABLE_ENTITY`, issue `REAUTHORIZATION_TOO_SOON`. Nothing changes on the authorization.
- **Q3, how often: once, per PayPal's own error text.** The 422's description says a reauthorization is allowed only once, from day 4 to day 29 after the original authorization. PayPal's docs ("Reauthorize authorized payment") say multiple reauthorizations are possible. The error text is the more specific source, so plan on **one** refresh per pool. **[verify]** on the retry, by trying a second reauthorization.
- **Q3, from which ID and what carries over:** not yet answered. A partly captured authorization (`PARTIALLY_CAPTURED`) got the timing refusal, not a "partly captured" refusal. That suggests partial capture alone does not block it. **[verify]**
- **Q4 (void on a reauthorized hold):** not yet answered.
- **Client change:** `REAUTHORIZATION_TOO_SOON` is now in `UNSUPPORTED_ISSUES`, so a too-early refresh is `unsupported` (nothing happened), not `unknown`. Without this, arch 5.5 would leave a pool stuck in `refreshing`, replaying forever.

## For Kitty

- **A hold can't be refreshed early.** S44's lead time must be "on or after day 4", never "before `honor_ends_at`". The 3 days before that can't be protected by reauthorizing. Arch 5.5 says the tick picks pools "nearing `honor_ends_at`". It should pick pools *past* it.
- **Assume one refresh per pool.** A pool's money is firm for days 1 to 3 and, after one refresh, for a few more days. After that it rests on "capture may still succeed" until day 29. The 28-day term cap stays, but the "hold needs refreshing" warning will be the normal state late in a pool's life.
- **No hold refresh can be shown before the Nov 12 deadline.** This was already planned for (arch milestone 5, S47b).
- Arch 5.5, ADR-0003 and Q3's row in arch 10 are left for S08, as S05 did.
