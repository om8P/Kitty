## What the code provides

- `Dockerfile`: a multi-stage `node:22-alpine` build that runs Next's standalone server as the non-root `node` user on port 3000. No secrets are used at build time.
- `.dockerignore`: keeps `.env*` (except `.env.example`), `.git`, `.claude`, `.spike-logs`, docs and `node_modules` out of the build context.
- `next.config.ts`: `output: "standalone"`. `npm start` still works locally, with a warning from Next.
- `/api/health` returns `{ status, db, dbTls, uptimeSeconds }` and logs `health ok db=<status> tls=<tls>` on each call.
  - `db` is `ok`, `error` or `unconfigured`, and it never contains error text.
  - `dbTls` is `verified` when `DATABASE_CA_CERT` is set, and `off` otherwise.
  - A database failure still returns 200.
  - A reset `uptimeSeconds` shows the instance restarted or slept.
- `src/db/connection.ts`: builds the `pg` settings. When `DATABASE_CA_CERT` holds the database's CA in PEM form, connections use TLS with full certificate checks. Keep `sslmode` out of `DATABASE_URL`, because `pg` lets URL parameters override these settings.
- `.github/workflows/schedule.yml`: calls `<KITTY_BASE_URL>/api/health` every 5 minutes, and can also be run by hand. It does nothing until the `KITTY_BASE_URL` repo secret exists, and it only runs from `main`.

## Owner guide

You do these steps in your own accounts. Agents never enter credentials or see the database password. **If any screen asks for a card or payment method, stop, add nothing, and tell the agent.**

Pick matching regions so the app and database are close, for example Render **Virginia (US East)** with Supabase **East US (North Virginia)**.

### 1. Supabase (database)

1. Sign up at supabase.com. Signing in with GitHub is fine.
2. Create an organization on the **Free** plan.
3. Create a project:
   - Name: `kitty`.
   - Database password: generate one and keep it in your password manager.
   - Region: as above.
4. **Connection string.** Open the project's **Connect** panel and copy the **Session pooler** URI. It looks like `postgresql://postgres.<ref>:[YOUR-PASSWORD]@aws-0-<region>.pooler.supabase.com:5432/postgres`. Put your password in place of `[YOUR-PASSWORD]`. Don't add `?sslmode=...`.
   - Use the session pooler, not the direct connection: the direct connection is IPv6-only on the free plan.
5. **CA certificate.** In **Project Settings → Database → SSL Configuration**, download the certificate **[verify UI name]**. Open the file in Notepad and copy everything, from `-----BEGIN CERTIFICATE-----` to `-----END CERTIFICATE-----`.
6. In the same section, turn on **Enforce SSL on incoming connections** if it's offered.

### 2. Render (app)

1. Sign up at render.com with GitHub.
2. Click **New → Web Service** and connect GitHub, giving Render access to the `om8P/Kitty` repo only.
3. Set the service:
   - Name: `kitty`.
   - Region: as above.
   - Branch: `main`.
   - Language (runtime): **Docker**.
   - Dockerfile path: `./Dockerfile`.
   - Instance type: **Free**.
4. Environment variables:
   - `DATABASE_URL`: the session pooler URI from Supabase step 4.
   - `DATABASE_CA_CERT`: the certificate text from Supabase step 5. A multi-line value is fine.
5. Leave **Health Check Path** empty. Render checks it every few seconds, and each check would query the database.
6. Create the service and wait for the first deploy.
7. Copy the service URL (`https://<name>.onrender.com`).

### 3. GitHub (schedule)

1. In the repo, go to **Settings → Secrets and variables → Actions → New repository secret**.
2. Name it `KITTY_BASE_URL` and set the value to the Render URL.
3. Go to **Actions → Schedule → Run workflow** to try it once.

### 4. Tell the agent

- Say it's deployed, and give the Render URL in chat. It won't be committed.
- Share these as text or screenshots, or open them in the built-in browser pane for the agent to read:
  - the build time from the deploy log
  - the memory graph from the Metrics tab
  - any limits Render shows on the Billing page's "Monthly Included Usage"
